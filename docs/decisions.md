# 设计决策记录

每条记录：**背景 → 决策 → 被否决的方案 → 后果**。
被否决的方案要留着——它们的失败原因正是后来者最需要知道的。

---

## D1 纯 Go + 零第三方依赖 + 无 cgo

**背景**：需要调大量 Win32 API，还要能从 Linux 交叉编译出 Windows exe。

**决策**：全部走 `syscall.NewLazyDLL` + `LazyProc.Call`，不引 `golang.org/x/sys/windows`，不引 `go-ole`。

**被否决**：
- `golang.org/x/sys/windows` —— 它确实更方便，但只覆盖一部分 API，混用两套风格比统一裸调更乱。
- **cgo + 一个 C 封装**（例如把 UIA 逻辑写成 C）—— 一旦引入 cgo 就要装 mingw-w64，`GOOS=windows CGO_ENABLED=0 go build` 这条从 WSL 一键出 exe 的链路就断了。宁可在 Go 里手写 COM vtable。

**后果**：
- ✅ `CGO_ENABLED=0` 交叉编译可用；无 `go.sum`；构建快
- ❌ **`-race` 不可用**（需要 cgo）。跨线程状态只能靠人读，不能靠工具验证——这是本项目最实在的代价，见 `design-debt.md`
- ❌ 需要自己维护结构体 ABI、HRESULT/BOOL 判定约定、COM vtable 槽位

## D2 原生 Win32 分层窗口，不上 Tauri / WebView2

**背景**：参考实现（有道）是 Tauri 2 + WebView2。Web 技术栈写 UI 明显更快。

**决策**：自己 `CreateWindowExW` + `UpdateLayeredWindow`。

**被否决**：
- **Tauri**：为了一个 4 项的菜单拖进 Rust 工具链 + WebView2 运行时依赖，且**窗口样式不可控**——Tauri 自己创建窗口，等你能 `SetWindowLongPtrW(GWL_EXSTYLE)` 补 `WS_EX_NOACTIVATE` 时，窗口已经显示过一次、可能已经抢过焦点了。而"不抢焦点"是本项目的硬要求。
- **WebView2 直接挂**：同上，库拥有窗口，拿不到创建时的样式控制权。

**后果**：
- ✅ `WS_EX_NOACTIVATE` / `SWP_NOACTIVATE` 全程可控；体积 2MB、无运行时依赖
- ❌ 视觉全靠手写：距离场圆角、阴影、文字遮罩（见 D3、D11）
- ❌ 要写窗口消息循环、命中测试、hover/press 状态机

## D3 软件渲染（距离场），不上 D2D / GDI+

**背景**：要圆角 + 柔和阴影，必须逐像素 alpha（分层窗口）。

**决策**：自己算圆角矩形的有符号距离场，阴影用高斯衰减。约 200 行纯数学。

**被否决**：
- **GDI+**：要绑 `GdipCreateFromHDC`/`GdipFillPath`/`GdipDrawString` 一大串扁平 API，比距离场代码还多。
- **Direct2D**：重，且对"画一个圆角矩形+阴影"是过度方案。
- **普通窗口 + `SetWindowRgn` 圆角**：没有阴影，且 16px 圆角的锯齿肉眼可见。

**后果**：
- ✅ 零依赖、完全可控、抗锯齿质量由自己决定
- ✅ 可以导出裸像素做逐像素验证（`-dump`）
- ❌ 字体渲染要绕过 GDI 不写 alpha 的限制（D11）

## D4 剪贴板自己逐格式快照，不用 OLE 代理

**背景**：剪贴板法必须先存下用户原本的剪贴板内容，用完还回去。第一版用 `OleGetClipboard` 存 `IDataObject`、`OleSetClipboard` 还原。

**症状**：实测约 **6/7 次还原失败**（`CLIPBRD_E_CANT_OPEN` / `CANT_CLOSE`），而且**会连累下一次取词**——还原失败时剪贴板可能被留在打开状态，下一次 `OpenClipboard` 就失败。用户侧表现是"划词弄丢了我的剪贴板"。

**根因**：`OleGetClipboard` 返回的是**代理对象，只在剪贴板未被修改期间有效**。而我们紧接着就发 Ctrl+C 把剪贴板换掉了，代理当场失效，`OleSetClipboard` 必然失败。

**被否决的补救**：先 `OleGetClipboard` 再 `OleFlushClipboard`。无效——`OleFlushClipboard` 只对"本进程自己放进剪贴板的数据"有意义，对别人拥有的剪贴板是空操作。**也否决了"加重试"**：这不是瞬时竞争，是语义错误，重试治不了。

**决策**：`EnumClipboardFormats` 逐格式快照。HGLOBAL 类格式拷字节；`CF_BITMAP` 用 `CopyImage` 复制一份（它不是 HGLOBAL）；还原时 `EmptyClipboard` + `SetClipboardData` 逐个写回。

**后果**：
- ✅ 无代理，行为确定；实测 6/7 失败 → 0
- ✅ 顺带修掉一个分类 bug：`CF_METAFILEPICT` / `CF_DSPMETAFILEPICT` 常被误当 GDI 句柄，其实是 HGLOBAL
- ❌ 要自己维护格式分类表与体量上限（单格式 32MB / 总量 96MB）
- ❌ 非 HGLOBAL 的格式（`CF_PALETTE` / `CF_ENHMETAFILE`）仍无法还原

## D5 剪贴板优先，MSAA 兜底（顺序不可反）

**背景**：两种手段都能"拿到文字"，但拿到的是不同的东西。

**决策**：先剪贴板，失败再 MSAA。

**为什么不能反过来**：**MSAA 没有选区 API**。`AccessibleObjectFromPoint` 给你的是"鼠标点所在的那个元素/词/行"。把它放在前面，会让浏览器/编辑器里本来很准的"精确选区"退化成"这一行"——把已经对的行为弄坏。

**后果**：
- ✅ 主流场景（浏览器 / 编辑器）保持精确选区
- ✅ Ctrl+C 不是复制的场景（VS Code 集成终端）由 MSAA 补位
- ❌ 即使在 MSAA 能work的场景，也要先付一次 Ctrl+C 的副作用代价

## D6 先 MSAA，后 UIA

**背景**：UIA `TextPattern` 才是"划词"的完全体（精确选区 + **选区矩形**）。但有道用的是 MSAA，且 Go 生态没有可用的 UIA 绑定。

**决策**：先 MSAA（本阶段已做），UIA 留作下一步。

**理由**：`IAccessible` 是 **IDispatch 派生**——vtable 前 7 槽是 IUnknown + IDispatch，后 21 槽是 `acc*` 方法，顺序自 Win95 起固定。按序号取函数指针直接调即可，**完全不用实现 `IDispatch::Invoke` 的参数封送**。

UIA 的 `IUIAutomationTextPattern` / `IUIAutomationTextRange` / `IUIAutomationTextRangeArray` 三个接口都要手写 vtable，方法更多，**顺序抄错一位就跳到错误的函数地址上，直接崩**。成本差一个量级。

**后果**：
- ✅ 低成本拿到"VS Code 终端"这类场景
- ❌ MSAA 拿不到选区矩形 → 弹窗只能猜鼠标点
- ⚠️ 已被评审确认：**当前结构下接 UIA 不是"加一个实现"，而是要第 4 次、紧接着第 5 次改 `captureSelection`**。所以 UIA 之前必须先做 `TextSource` 抽象（见 `design-debt.md` 第 1 项）

## D7 真控制台：剪贴板禁用，但 UIA 照试

**背景**：cmd / PowerShell / Windows Terminal 里取文。

**关于 Ctrl+C 在控制台里的真实语义（一度被我写错，这里更正）**

它不是无条件的中断，而是**上下文相关**的：

| 有没有选区 | Ctrl+C 的含义 |
|---|---|
| **有选区** | 复制（VS Code 终端 / Windows Terminal / conhost 的 QuickEdit 都如此）|
| 无选区 | 发送 `\x03` = 中断信号 |

而我们发 Ctrl+C 的时机永远是「用户刚拖选完、选区还在」，所以**它通常被解释成复制**。
实证：VS Code 终端那次划词拿回了选中文本（`IP address: 192.168.2.104`）——
若真发成了中断，剪贴板不可能变成选中内容。

**那为什么仍然对真控制台禁用**：因为**窗口期**。流程是「鼠标抬起 → 等 160ms → 发 Ctrl+C」，
若选区在这 160ms 内消失（终端输出滚动、用户误点别处），Ctrl+C 就**真的**变成中断，
把用户正在跑的命令杀掉。持续输出的场景（如 `ping -t`）最容易踩到。
代价不对称：取不到词无所谓，杀掉用户的命令不可接受。

**一个我承认的不一致**：同一个机制（Ctrl+C 在有选区时=复制），
我在 VS Code 终端里信任它、在 Windows Terminal 里禁止它 —— 差别不在原则，
只在于 **VS Code 的终端藏在 `Chrome_WidgetWin_1` 里、与编辑区无法区分所以拦不住**，
而 Windows Terminal / conhost 有独立类名、拦得住就拦了。这是"能拦则拦"的实用主义。

**真正的解法**（尚未实现）：用 `AttachConsole` + `GetConsoleSelectionInfo` 先确认
「此刻确实有选区」再发 Ctrl+C，那样就不必靠窗口类名一刀切，窗口期的风险也消失。
- **用 MSAA 兜底**：实测返回的是**控制台窗口自身的名字/整块缓冲区**，不是用户拖选的选区
  （用户实测反馈"能弹出但文本不对"）。**弹一个内容不对的菜单比不弹更糟**。→ 否决。

**第一版结论（已被推翻）**：前台是控制台窗口时什么都不做。
第一版把**所有**手段一起关掉了，这是过度收缩。

**修正后的决策**：按「有没有副作用」分而治之，而不是按「是不是控制台」一刀切。

| 手段 | 控制台里 | 理由 |
|---|---|---|
| 剪贴板 | ❌ 禁用 | 会发 Ctrl+C = 中断用户的命令 |
| MSAA | ❌ 禁用 | 返回窗口自身信息而非选区 |
| **UIA** | ✅ **照试** | **只读**，零副作用；试一下代价为零 |

能这么分，是因为三者的副作用性质不同 —— 之前的错误是拿"环境"当判据，
而正确的判据是"这个手段在这个环境里会不会造成伤害"。

**实测结果**（Windows Terminal 里跑 `ping -t` 然后划选输出）：

```
drag @(1494,794)  →  来源=uia  17 字  "字节=32 时间<1ms TTL="   耗时 64ms
```

控制台通了，而且因为走的是 UIA，那次划词**根本没发 Ctrl+C** —— ping 从原理上就不可能被打断。

**守门**：先问 provider `GetSupportedTextSelection`，返回 `None(0)` 就直接放弃，
避免重演 MSAA 那次"弹出内容不对的菜单"。

**实测补充（关于「不抢焦点」）**：在 VS Code 编辑区 / VS Code 终端 / 浏览器三处各划一次，
日志里的 `[focus] 菜单显示后前台窗口仍是 …（未抢焦点）` 三处全部成立；
更早一轮 13 次划词也是 13 次未抢焦点。**终端里选区消失不是抢焦点造成的**
—— 终端在 Ctrl+C 复制之后自己清掉了选区（编辑器复制后则保留高亮，
这就是"只有终端有问题"的原因）。

> 这也是为什么日志要带**窗口标题**而不只是类名：VS Code、Chrome、Edge、Slack 的窗口类名
> 全都是 `Chrome_WidgetWin_1`，光看类名根本分不出这次划词发生在哪个程序里。

**仍然没做的**：控制台 API（`AttachConsole` → `GetConsoleSelectionInfo` →
`ReadConsoleOutputCharacterW`）。UIA 已经把这条覆盖了，除非遇到 UIA 读不到的终端才需要。

## D8 绝不抢焦点

**背景**：弹出菜单时如果激活窗口，源程序的**选区高亮会消失、选区也可能被清掉**，之后的 Ctrl+C 就复制不到东西了——等于把取文的前提毁掉。

**决策**：
- 窗口样式 `WS_EX_NOACTIVATE | WS_EX_TOOLWINDOW | WS_EX_TOPMOST | WS_EX_LAYERED`
- 显示一律 `SetWindowPos(..., SWP_NOACTIVATE | SWP_SHOWWINDOW)`，**绝不用 `ShowWindow(SW_SHOW)`**（`ShowWindow` 没法带 `SWP_NOACTIVATE`）

**后果**：
- ✅ 源程序选区保持
- ❌ 窗口拿不到键盘焦点 → 菜单上的快捷键（`Ctrl+C` / `Enter` / `Ctrl+T`）**目前只是展示，没有接线**。要接线只能上键盘钩子

## D9 构建戳 + 版本自证（否决 md5 比对）

**背景**：真踩过——打完补丁只 build 到临时文件，却把旧的 `clickr.exe` 部署了出去，用户测的全程是旧版。而我当时的校验是「源文件与目标文件 md5 一致」。

**为什么那个校验无效**：它只证明"复制没出错"，**证明不了"源文件是新的"**。校验了一个错的不变量。

**决策**：
1. `build.sh` 每次注入时间戳到 `main.buildStamp`，构建后 `grep` 二进制确认戳真的写进去了，不一致就 `exit 1`
2. 提供 `-version`，让**部署后的产物自报身份**
3. 启动日志第一行就打构建戳

**后果**：
- ✅ "部署的是哪个版本"变成可机械回答的问题
- ✅ 启动日志里能看到构建戳，排查时不用再猜
- ⚠️ 仍然依赖"部署时记得比对"——没有做成自动闸门

## D10 窗口留白从阴影参数反推

**背景**：窗口必须比可见卡片大出投影的扩散距离，否则阴影被窗口边界**硬切出一条直边**。

**症状**：留白写死 18px，而实际投影扩散需要 21.4px（`blur=12, dy=5`）。球体下方 alpha 到 48 就断崖——肉眼可见。

**决策**：`shadowReach(blur, dy) = blur*1.2 + |dy| + 2`，`menuShadowPad()` / `ballShadowPad()` 都从它反推。

**为什么是 1.2×blur**：σ = blur/2，`d = 1.2·blur` 时高斯权重已降到 `exp(-2.88) ≈ 5.6%`，再乘阴影自身 alpha 后不可见。1.5× 是浪费窗口面积。

**后果**：✅ 留白与阴影参数永远同步，有测试守着（`TestWindowPadCoversShadow`）

## D11 文字用灰度抗锯齿 + 亮度当覆盖率

**背景**：`UpdateLayeredWindow` 用**预乘 alpha**，而 **GDI 往 32bpp DIB 上画东西时不写 alpha 字节**（一直是 0）。直接 `DrawTextW` 画字 → alpha=0 → **一个字都看不见**。

**决策**：文字走"黑字白底渲染到 scratch → 用亮度反相当覆盖率 → 手动合成"。

**因此**：字体质量必须是 `ANTIALIASED_QUALITY`（灰度抗锯齿），**不能用 ClearType** —— ClearType 会产生彩色子像素，直接破坏"亮度当覆盖率"这个前提。

**被否决**：给 GDI 画过的像素做 alpha 后处理（无法区分背景与文字）；用 GDI+ 直接支持 alpha（见 D3）。

**后果**：✅ 抗锯齿文字 + 正确 alpha；遮罩按 `(文本, 尺寸, 字体)` 缓存 ✅
❌ 每个新字符串首次显示要建一个 DIB；缓存无上限（实际字符串集合有界，安全但不显式）

## D12 视觉规格仿豆包，但品牌色用鸢尾蓝（取值靠量 token，不靠看截图）

**背景**：菜单原本照有道词典的 AI 助手抄（配色、圆角、阴影数值都来自它的前端 CSS）。
要求改成「仿豆包那套插件弹层」的观感，同时明确：**只仿，不搬**——色调要用鸢尾蓝。

**决策**：分两层处理。

1. **中性层级与几何照豆包的 token**（实测，不是估的）。从豆包官网 `chat.css` 里量到：

   | 用途 | 取值 | token |
   |---|---|---|
   | 卡片底色 | `#FFF` / 暗色 `#232528` | `--s-color-bg-float` |
   | 卡片 / 悬停项圆角 | 16px / 12px | `--s-radius-m` / `--s-radius-s` |
   | 投影 | `0 0 4px rgba(0,0,0,.02)` + `0 10px 24px rgba(47,53,64,.2)` | `--s-shadow-level2` |
   | 标题 / 快捷键 | `rgba(0,0,0,.85)` / `rgba(0,0,0,.3)` | `--s-color-text-secondary` / `-quaternary` |
   | 悬停底色 | `#F5F5F5`（暗色 `rgba(255,255,255,.06)`） | `--s-color-bg-outlined-btn-hover` |
   | 渐变描边的角度与做法 | 1px、`linear-gradient(301deg, …)` | `--s-color-ai-line` |

2. **品牌色换掉**。主色 = **鸢尾蓝 `#49589C`**（RAL 290 40 40，色号官方中英文名即「鸢尾蓝 / Iris blue」）；
   卡片描边是这抹鸢尾蓝的渐变（浅端 `#B6BCD7` = 鸢尾蓝与白混 60%）。
   悬浮球中心保持本项目自己的四角星标记，只是换成鸢尾蓝 —— 不引入豆包的 logo 位图。

**为什么用 token 而不是"对着截图抄"**：
我这侧没有图像输入能力，看不到截图，**肉眼比对这条路根本不成立**。
CSS token 是可下载、可复述、可写进测试的**数据**：`#49589C` 能被逐像素断言，截图不能。
这也是本项目一贯的做法（"vtable 顺序能测就别推"）。

**被否决的方案**：
- **把豆包官方 logo 位图当球心图标**（`favicon/new-doubao/192x192.png`，实测过：浅蓝圆底 + 卡通形象，192px 是它 CDN 上最大的尺寸）。
  否决原因：要求就是"仿、不是全用"，而且引入第三方品牌位图要连带引入 `go:embed` + PNG 解码 + 缩放采样一整套东西 ——
  为了一个 18px 的标记不值得，手画的距离场图元在任意 DPI 下还更干净。
- **只换配色、不改图标画法**。否决原因：翻译图标当时是**直接拿字体画**的「文A」，
  笔画粗细与端点跟着字体走，和另外两个描边图标不是一套语言。既然要"仿那套线性图标"，就得连画法一起改。
- **把菜单改成豆包那种横向工具条**（当时否决）原因：动布局要连带动 `menuItemRect` / 命中测试 / `placeMenu` 与一批测试，
  而收益只是"更像"，风险却落在已经稳定工作的交互上。
  > **这条已被 D13 推翻**：用户明确要求改横向。事后看，当时的成本估计是对的 ——
  > 交互（hover/点击/离开判定）、命中测试、`placeMenu` 与菜单测试确实全都要动；
  > 但收益不只是"更像"：面积降到约 1/3.5，贴在大段选区旁边不再压住内容。

**后果**：
- ✅ 改色调只动 `appearance.go` 顶部两个常量（`irisBlue` / `irisBlueLight`），几何与绘制代码不碰
- ✅ 视觉规格第一次有了**可断言的形式**：`TestMenuRenderShapeAndHover` 断言描边是蓝色系，
  `TestBallRenderShape` 断言球心就是主题里的标记色（不再写死某个品牌色）

## D13 菜单改横向工具条；「划词弹出」的开关入口放在悬浮球上

**背景**：竖向菜单（185×128）贴在全选一大段文字旁边时占地太大，压住内容；
而且它只有三个动作，竖排是在浪费高度。同时需要一个「关掉划词自动弹菜单」的开关。

**决策**：

1. **横向工具条**：`复制 / 搜索 / 翻译 / …`，每项「图标 + 文字」横排。
   单项 26px + 内边距 4px → 整条 **34px 高（原 128px）**；宽度**按内容算**
   （`barItemWidth` 用 `textWidth` 量文字），不再是写死的常量。
   `…` 点开/悬停展开一块**二级面板**（竖列表，宽度与工具条对齐），放低频动作。
2. **窗口高度按展开态预留**：收起时下面那块是 alpha=0 的透明区。
   这样悬停展开时不必改窗口尺寸（改尺寸要重建 surface + 重新 present + 重排位置）。
   透明区不吃鼠标消息，所以不影响下面的程序。
3. **面板不跟 WM_MOUSELEAVE 收起**：工具条与面板之间那条 6px 的缝是透明的，
   指针过缝时窗口**必然**收到 leave；跟着 leave 收面板，面板会在指针到达前先消失。
   改为：leave 时看指针还在不在 `menuBlockRect`（两块卡片的外接矩形，含缝）里 ——
   在，说明是去过面板；不在，才是走开了，这时才收起。
4. **开关的入口分两处**：
   - **关**：划词菜单 `…` → `关闭划词弹出`（标题不写"关闭"，因为那会被读成"收起菜单"）
   - **开**：**单击悬浮球**。理由：功能一关菜单就再也不出现，**球是唯一还在屏幕上的东西**。
     球心标记同时是状态灯：开着=鸢尾蓝，关着=中性灰。
5. **关掉之后连取词都不做**：判断放在**钩子回调**里，不在渲染菜单那一步 ——
   取词要发 Ctrl+C、要动剪贴板，功能关了还去动用户的剪贴板说不过去。
6. **开关持久化用"文件存不存在"**（`%AppData%\clickr\popup.off`）：
   默认值是"开"，于是"第一次运行""用户删了文件""文件写坏了"全是同一件事，不用写分支。

**被否决的方案**：

- **二级面板开第二个窗口**。否决原因：得把 `menuSurf` / `menuModel_` / `menuPos` /
  hover / pressed 这一整套状态再来一份，而它们现在都是全局变量（见 design-debt 第 1 项）——
  在已知会出问题的地方再复制一份，不如让同一块 surface 多画一张卡片。
- **展开时改窗口尺寸**（收起时窗口就是工具条那么高）。否决原因：hover 是高频路径，
  改尺寸要重建 surface、重新 present、还要重排位置；而多出来的透明区是免费的。
- **`…` 只在点击时展开**。否决原因：悬停展开是这类浮层的通用预期，
  真正要解决的是"过缝被判成离开"，那是 leave 的判据问题（见决策 3），不是展开时机的问题。
- **把开关做成托盘图标 / 设置窗口**。否决原因：为布尔量引入托盘或二级窗口，
  比"球本身变灰 + 点一下就开"重得多。

**后果**：
- ✅ 工具条面积从 185×128 降到 ~198×34（≈1/3.5），且宽度随内容自适应
- ✅ 状态可见（球心颜色）+ 入口唯一且不会丢（球一直在屏幕上）
- ✅ 新增 `config_test.go` 守持久化往返；`TestMenuBarIsShortAndContentSized` 守"必须是扁的、宽度必须随内容变"
- ⚠️ 面板只向下展开、不向上翻：整块被夹进工作区，贴屏幕底部划词时工具条会离选区远一点
  （要治得在 `placeMenu` 里做上下对调的分支）
- ⚠️ 同时多了一块"布局依赖 GDI 量文字"的耦合：`barItemWidth` 与渲染必须用同一个字体句柄，
  实测在 125% DPI 下两者不一致会让文字和悬停底色错位（所以字体句柄收敛到 `barFont()`）

### 修订（同日，第一轮实看之后）

第一版交上去之后有三条直接的反馈，都是**看屏幕看出来的**，token 里量不到：

| 反馈 | 处理 |

## D14 弹窗锚点用鼠标点，菜单贴在鼠标正下方一行

**背景**：菜单原先贴在锚点的右下方 8px，而锚点在 UIA 能给出选区矩形时取的是**选区末尾那个矩形**
（当初的理由：反向拖选时它比鼠标抬起点准，见 D6 一带的记录）。实际用起来，用户要的是
"菜单就出现在我刚操作的地方"。

**决策**：

1. **锚点 = 鼠标那一下的位置**（拖选的抬起点 / 双击的第二下）。`captureResult.anchor` 本来就是它，
   `main.go` 里那段"有选区矩形就覆盖锚点"的逻辑删掉。
2. **贴在鼠标正下方一行**：`menuAnchorGapY = 20px`，左边与鼠标 x **对齐**（`menuAnchorGapX = 0`）。
   让开一行是为了不压住光标、也不盖住刚选中的那几个字；左右不再留偏移，
   因为"鼠标一停，条就在它底下"比"右下角 8px"更符合预期。
3. 翻转与夹取保留：右边放不下翻到鼠标左边、下面放不下翻到鼠标上面，最后整块夹进工作区。
4. **选区矩形不丢**：仍然记进日志（`[capture] 选区矩形 …（只记日志，不再当锚点）`），
   排查"菜单弹歪了"时它是第一手证据。

**被否决的方案**：

- **保留选区矩形当锚点**。它在"选区很长、鼠标停在中间"这类情况下的确更贴选区，
  但那是**实现视角的"准"**，不是用户视角的"对"：用户刚在某个点上松手，菜单却从选区末尾冒出来，
  感觉是"弹到别处去了"。
- **右下角留 8px 偏移**（原来的做法）。横条本来就矮，右下偏移让它在视觉上和鼠标错开一格，
  既不像"跟着鼠标"，也不像"贴着选区"，两头不靠。
- **让用户选**（比如加个设置项）。为 20px 的偏移引入一个配置项、一个持久化字段、
  一套测试，收益不成立。

**后果**：
- ✅ 行为可预期：鼠标停在哪，条就在它下面一行；不再依赖 UIA 是否给出选区矩形
  （以前"有没有 bounds"会让菜单出现在两个不同的位置，这本身就不该）
- ✅ 定位与取文手段**解耦**：剪贴板法 / UIA / MSAA 走哪条路都不影响菜单出现在哪
- ❌ 选区很长时（比如全选一篇文档），鼠标停在文档中间松手，菜单就出现在中间 ——
  而不是贴着选区末尾。这是这次选择的直接代价，认了
- ⚠️ 20px 是"一行"的近似值：它按 13px 字体加行距估的，不是量出来的

2. **技能本体**：豆包的技能表里有 `explain 解释 / summarize 总结 / grammar 校对 /

  没有 CSS 引擎；能搬的是**数值**，不是规则。
- **把技能的 prompt 存进配置、点开时打开某个网页**。那是个假功能。

**后果**：
- ✅ 工具条/二级菜单/禁用/设置页的数值第一次有了**明确出处**（哪个文件、哪条规则），

- ✅ 设置页做成"一个 `settingsRows()` 切片决定内容"，用户说了具体项以后要改随时改
- ⚠️ 技能表跟豆包只对齐了"能干活的那四个"；解释/总结/朗读这些**故意没做**，见上
- ⚠️ 豆包的设置页还有"在此网站中禁用/禁用应用列表/发现更多技能"这些分站点、分应用的设置，
  本项目没有站点/应用维度的配置，所以没抄

### 修订（同日，又看了一次屏幕）：尺寸整体缩到 0.7

抄完之后用户的第一句反馈是「**字太大，图标太大**」。抄的数值没错 —— 是**场景不同**：

| | 豆包（网页浮层） | 本项目（桌面划词工具条） |
|---|---|---|
| 单项高 | 40 | **28**（内边距 6 + 图标 16 + 6） |
| 图标 | 24 | **16** |
| 文字 | 18px | **13px** |
| 整条高 | 44 | **32** |
| 卡片 / 项圆角 | 14 / 12 | **10 / 8**（仍同心） |
| `…` 按钮 | 40×40 | **32×28** |
| 竖分隔线高 | 32 | **22** |

它那套是给**网页里浮在正文上的按钮**定的尺寸（要压得住网页的字号），
我们这条是贴在选区边上、桌面程序里的辅助条，同样的绝对值就偏胖。

**所以"抄"这件事的边界在这里**：抄的是**结构与关系**（谁是内边距、谁是图标、谁管分隔、

`TestMenuBarIsShortAndContentSized` 现在断言 32 / 图标 ≤20 / 文字 ≤15，把这一档钉住。

### 修订（同日，评审之后）：图标改 emoji + 修掉评审抓到的缺陷

用户反馈「翻译图标丑爆了，这几个图标你能找找 emoji 吗」。改成 emoji：

| 图标 | emoji |
|---|---|
| 复制 / 翻译 / AI 搜索 / 问问豆包 | 📋 / 🌐 / 🔍 / 💬 |
| 设置 / 启用 / 退出 | ⚙ / ✅ / 🚪 |
| 禁用 | **不用 emoji** —— 仍是照豆包 CSS 画的那个小叉（24×24 圆角底 + 12px 的 ×） |

实现上有个关键点：**GDI 画 emoji 给的是单色轮廓**（它不支持 COLR/CPAL 彩色字形），
这恰好是本项目需要的 —— 文字遮罩那套就是"把亮度当覆盖率"，彩色字形反而会算错。
所以 `emojiFont()` 直接复用了 `fontFace()` 那条路，只是换了个字体系列。
改图标现在只改 `iconEmoji` 那张表；`TestEmojiIconsRenderInk` 会逐个验证"真的画出了墨迹"
（字体缺失或字形不存在时图标会变成空白，那种事必须被测试拦住，而不是等用户看见）。

同轮按评审（Standards / Spec / UI 三轴）修掉的缺陷：

- **主题块被编辑事故写坏**：浅色分支漏设 `bodyText` → **设置页整页正文 alpha=0，看不见**；
  暗色分支 `label` 被写成鸢尾蓝本体（压在 `#232528` 上只有 2.31:1）而文档写的是浅端；
  还有一句死赋值和拼坏的注释。根因是一次 `strings.Replace` 拿 `"th.label = irisBlue"`
  去替 `"th.label = irisBlueLight"` 的**前缀**。测试也跟着收紧了：暗色必须是浅端、两套主题都必须设 `bodyText`。
- **禁用之后设置页不可达**：`appMenuItems` 把「自定义设置」也一起藏了，而禁用后划词条不再出现 → 死胡同。改成设置项常驻。
- **点「…」反而把整条菜单收掉**：`isMore` 不产生动作，但后面无条件 `hideMenu()`。改成点它只展开、不收菜单。
- **悬浮球单击被手抖吃掉**：任何 1px 位移都算拖动。加了 3px 阈值，并补上 `SetCapture`/`ReleaseCapture`
  与 `WM_CAPTURECHANGED` 复位（README 早就写着"SetCapture"，代码里其实没有 —— 文档又跑在实现前面了）。
- **球菜单里「禁用/设置」出现两次**：`ballMenuModel` 在 `selectionMenu` 已经带了这两项的情况下又 append 了一遍。
- **设置页底部状态文案画到卡片外**：卡片高度改成按内容算（`settingsCardHeight()`）。
- **关闭按钮永不亮**：`settingsHit` 的返回值没接到渲染上。
- **日志行标题与路径叠在同一处**（改好主题后必然显形）：改成左标题、右路径；顺带把"打开日志目录"真的打开目录而不是文件。
- **对比度**：次要文字从 `rgba(0,0,0,.3)`（白底 2.1:1）提到 `.55`（≈4.7:1，过 AA）。
- **抄错的一处**：竖分隔线豆包写的是"盒高 32 + 上下 padding 8 + content-box"，**实际只画 16px**，
  我按 32 缩成了 22；现在按单项高度比缩到 12。
- **跨线程**：`settingsOpen` 改为在 `menuRectMu` 内发布（钩子线程在锁内读它）。
- 结构上把"菜单当前可见区域"收成一个 `menuVisibleRect()`（原来三处各写一遍 if），
  清掉死语句与无用参数，给设置页补了 `settings_test.go`、给技能持久化补了往返测试。

### 修订（同日，再次反馈）

- **二级菜单太宽**：它原本跟着工具条一样宽（318px），而里面只有「禁用 / 自定义设置」两项。
  改成**按自己的内容算宽度**（下限 132px），并**右缘与工具条对齐** —— 它是从最右边那个 `…` 掉下来的，
  挂左边会让人以为它属于第一个技能。窗口宽度改成取两者较宽者（菜单项更长时窗口跟着变宽，不许裁掉）。
  实测：工具条 318×32、二级菜单 **132×60**，右缘对齐。
- **「问问豆包」→「知识检索」**：不再是"复制文字 + 打开豆包对话页让用户自己粘贴"（那不叫检索，叫搬运），
  改成一次点击到位：拿选中的文字去百科检索（`baike.baidu.com/search?word=`，实测可达；
  维基百科在国内不可达，所以没用它）。技能 **id 保持 `ask` 不改** —— 它写在用户的 `skills.txt` 里，
  改 id 会让那份配置失配（认不出的 id 会被当成"这个技能是关的"）。图标随之改成 📚。

### 修订（同日，再一条反馈）：鼠标停在悬浮球上自动出菜单

用户说豆包那个手感很好（「鼠标放悬浮球上自动出现下拉的菜单」），照做。三点值得记：

1. **弹出要延时（180ms）**：球常驻在屏幕边上，鼠标经常从它身上划过去；不延时的话路过就弹一下。
2. **收起也要延时（320ms），而且判断放在"到点那一刻"**：从球挪到菜单要跨过一段**不属于任何窗口**
   的空隙（那里收不到鼠标消息），所以不能"一离开球就决定收"；到点时再看一眼鼠标在哪
   （`menuKeepsOpenAt`：在球上或在菜单矩形里就留着），才能把"正在往菜单挪"和"走开了"分开。
   这个形状和二级菜单那条"过缝去面板"是同一类问题的两种解法（那边靠"整块矩形"，这边靠"落点复查"）。
3. **顺便修了一个口径不一致**：`ballHoverGrow` 在绘制里被当成"直径增量"、在 `ballContains` 的判定区里
   被当成"半径增量"。表现是鼠标在放大出来的那一圈上反复进出。现在统一成**半径**增量，
   `TestBallGrowsOnHover` 直接量像素：悬停直径必须增大 `2*ballHoverGrow`（±2px 抗锯齿容差）。

顺带：设置页开着的时候不叠菜单（`hoverShowMenu` 里判 `settingsOpen`）。

## D16 右侧边栏：为什么它是只读的，以及 AI 临时问答要接的话得先决定什么

**背景**：需求是「左键单击悬浮球弹出右侧边栏」，并问"能不能用来做 AI 问答（那种临时问答，不是长会话）"。

**已做的部分**：侧边栏（`sidebar.go`），框架照豆包插件侧边栏抄（`side_panel.css`：
header `margin:14px 15px 6px 0`、内容 `padding:0 20px`、列表项 40px/圆角 12、底部输入区
`border:1px solid rgba(0,0,0,.08)`）。里面是：当前选中了什么（自动折行，最多 4 行）、
对它可以做的动作（直接来自技能表，所以设置页关掉的技能这里也不会出现）、开关状态、设置入口。
单击球 → 侧边栏；悬停球 → 球旁边的菜单；两者互斥（同时只留一块浮层）。

**为什么没有输入框** —— 这是这次最要紧的一个判断：

本项目所有窗口都是 `WS_EX_NOACTIVATE` 的**分层窗口**（D8：绝不抢焦点，抢了源程序的选区就没了）。
这种窗口拿不到键盘焦点，也就**没有输入法**。画一个点不动的输入框就是假可供性 ——
评审刚抓过同类问题（左栏导航画成可点、日志行文案与行为不符）。

**AI 临时问答的两条路**：

| | A：不接后端（现在这样） | B：接模型接口 |
|---|---|---|
| 问题从哪来 | **划词就是问题**（选中 → 点「问一下」），不需要打字 | 打字，或同样用划词 |
| 答案在哪 | 跳到浏览器（豆包/搜索/百科） | **流式显示在侧边栏里** |
| 需要什么 | 无 | 接口地址 / 密钥 / 模型名（从配置文件读，不能走我们的 UI）、HTTP 客户端（stdlib 足够）、流式渲染 |
| 代价 | 答案不在面板里 | 要处理"密钥怎么存""错误怎么显示"（本项目已知债：失败对用户不可见） |

**建议的顺序**：先做 B 的"划词当问题"版本 —— 它绕开了键盘与焦点这个硬约束，
而且和本项目的强项（拿得到精确选区）天然契合；**打字输入最后再做**，
它需要引入本项目第一种"普通窗口 + 原生 EDIT 控件"（IME 才有），
那是跨出"纯分层窗口"边界的一步，值得单独立项，不该混在侧边栏里顺带做掉。

**被否决的方案**：
- **在分层窗口里自绘输入框 + 自建输入法处理**。否决：光标、选区、输入法组合串全都得自己写，
  而 Win32 原生 EDIT 控件这些是白送的；自建一套的失败面比收益大得多。
- **嵌 WebView2 做聊天界面**。否决：违反 D2（不引运行时依赖），而且为此要手写 WebView2 的 COM 接口。
- **侧边栏里先放一个禁用状态的输入框示意**。否决：假可供性。

## D17 临时问答：OpenAI 兼容 + 配置文件 + 划词即问题；设置页为键盘输入破例

**背景**：需求是"侧边栏能不能用来做 AI 问答，那种临时问答，不是长会话"，并明确
"设置页面要给用户配置 url、key 和模型，模型用 DeepSeek 的"。

**决策一：接口走 OpenAI 兼容格式**。`POST {base_url}/chat/completions`，`stream: true`，读 SSE。
这样 DeepSeek / OpenAI / 火山方舟 / Ollama / LM Studio 用的是同一段代码，
换服务只改配置里的两行。默认预置 DeepSeek（`https://api.deepseek.com/v1` + `deepseek-flash`），
第一次运行就把 `%AppData%\clickr\ai.txt` 写好，**只差填 api_key**。

> 实测过：不带密钥请求 `https://api.deepseek.com/v1/chat/completions` 返回 **401**，
> 即该路径存在且是 OpenAI 兼容的（探测方式就是发一次无密钥请求看返回码）。

**决策二：问题来自划词，不做输入框**（"划词即问题"）。选中一段文字 → 侧边栏点「问一下」→
答案流式回显。理由：本项目的强项是**拿得到精确选区**，而打字输入要解决键盘焦点与输入法，
成本高得多（见下面的决策三）。"临时问答"这个词本身也支持这个形态：一次一段文字。

**决策三：一次性，不留历史**。再问一次就替换上一次（连问题带答案）。要历史就是"长会话"了，
那是另一个产品形态，不在这里顺带做。

**决策四：设置页破例改成可激活窗口 + 原生 EDIT 控件**。

这是本项目第一次违反自己的 D8（绝不抢焦点），所以必须写清边界：

- **为什么必须破例**：`WS_EX_NOACTIVATE` 的窗口拿不到键盘焦点，也就**没有输入法**。
  自己画输入框等于重写光标、选区、IME 组合串、剪贴板 —— 而 Win32 原生 EDIT 这些全是白送的。
- **破例范围**：只有 `hwndSettings`（`createLayeredWindowActivatable`，present 时不带 `SWP_NOACTIVATE`
  并 `SetForegroundWindow`）。菜单、悬浮球、侧边栏**不变**，仍然是 NOACTIVATE ——
  它们出现时用户正在别的程序里划词，抢焦点会清掉选区，功能就废了。
- **设置页不会在"划词时"自己冒出来**：它只能由用户主动点开（菜单里的「自定义设置」），
  所以抢焦点在这里是"你点了它"，不是"它来打断你"。
- **视觉仍然是自绘**：圆角、边框、底色由我们的渲染器画，EDIT 是**无边框**子窗口贴在框里，
  `WM_CTLCOLOREDIT` 里把文字色与底色设成和卡片一致 —— 看起来还是一块自绘输入框。

**被否决的方案**：
- **自绘输入框 + 自建 IME 处理**。否决：失败面太大，而收益只是"看起来更统一"。
- **嵌 WebView2**。否决：违反 D2，而且要手写 WebView2 的 COM 接口。
- **密钥存系统钥匙串**。本轮没做，用的是明文配置文件（文件头与 README 都写明了）。
  要做的话是"加密存储"这个话题，不该混在"加三个输入框"里顺带做。
- **让菜单/侧边栏也能打字**。否决：那等于把 D8 的例外扩大到会打断划词的那些窗口上。

**后果**：
- ✅ 从"选中文字"到"看到答案"全程不离开选区上下文；密钥不进代码、不进日志
- ✅ `-ask "问题"` 让这条路**可以被脚本验证**（本地假服务 + 断言，不必依赖真 key）
- ✅ 测试覆盖：配置往返、SSE 解析、请求体、过期流丢弃、停止语义、原生控件的建立与掩码
- ⚠️ 明文密钥文件；没有系统钥匙串
- ⚠️ 设置页现在会抢焦点（有意为之，范围仅此一处）
